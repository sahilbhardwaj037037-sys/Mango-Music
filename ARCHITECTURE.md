# Mango Music architecture — Checkpoint 7, Phase 3B

## Downloads ownership, storage and local-first playback

The application factory shares one `SQLiteLibraryStore` between `MusicLibrary` and the main-actor observable `DownloadManager`. `DownloadPersisting`, `AudioDownloading` and `AudioFileValidating` are injectable boundaries; tests supply temporary databases/roots and isolated settings. Downloads use independent metadata/revision transactions, so coalesced collection snapshots neither erase download records nor conflict with their own manager. Song metadata is copied into downloads rather than referencing the prunable `songs` table.

`DownloadManager` has one worker. Enqueue deduplicates stable IDs; each explicit retry receives a fresh UUID. State transitions are queued → downloading → validating → complete, with cancelled/failed/interrupted/missing/deleting states. A coalescing writer persists attempts before network IO and persists the validated intended path before publication. Only a complete record with timestamp, size, format and hash can resolve locally. Progress callbacks match both ID and attempt/status. Cancellation terminates/drains the owned process group before staging removal or another job; deletion waits for the same worker. Quit cancels queued/active attempts and awaits worker/write completion; failed saves cancel quit and offer Retry. Restart marks active rows interrupted, checks completed bytes/hash, finishes pending deletions and never starts downloads automatically.

`ManagedDownloadFiles` owns a private 0700 `Downloads` root and an exclusive nonblocking `.lock` advisory lease, claimed before loading/reconciling metadata. File descriptors and `openat`/`O_NOFOLLOW` reject root/subdirectory symlinks and traversal; the root inode is checked on reuse. Paths are strictly `media/<validated-video-ID>-<attempt-UUID>.<allowed-extension>`, never display titles or supplied absolute paths. Download bytes stay in `staging/<UUID>`; validation precedes exclusive `linkat` publication and file/directory fsync. Final files are 0600. Publication cannot overwrite an existing path; cleanup only addresses managed entries. Hashing and filesystem work run on the files actor, away from SwiftUI. Hash checks repeat at startup and local resolution; large libraries can take time to check.

`DownloadProcessRunner` uses argument arrays and `posix_spawn` with a private process group, bounded output buffers, periodic budget/free-space checks, and a 900-second default deadline. Cancel sends TERM, then KILL after one second, reaps the parent and drains pipes. No shell, cookies, user yt-dlp configuration, plugins, persistent yt-dlp cache or resume-in-place is enabled. Retries are explicit fresh attempts, with bounded downloader transport/fragment retries. Limits are 512 MiB per attempt, 5 GiB managed logical bytes including staging, and 256 MiB free reserve. Size checks are sampled, so a fast write can transiently exceed a threshold before termination. The displayed storage total counts complete records, while admission counts actual managed files (including leftover bytes).

`YTAudioDownloadService` selects audio-only native HLS first, then M4A, then other best audio. With no conversion executables it disables fixups and uses native HLS/MPEG-TS; extension is not treated as proof of container. `MPVAudioFileValidator` starts a separate bounded null-output decoder, requires a positive audio clock, known finite duration up to six hours, no non-artwork video, and a self-contained container. It rejects remote playlists; only file protocols and no external references are allowed. This probes decode/start, not a full-duration corruption scan. `VerifiedConversionTools` accepts native executable ffmpeg/ffprobe in the same directory; packaged lookup fails closed within the bundle. Verified tools enable conditional conversion of otherwise unsupported containers to AAC/M4A. Static FFmpeg libraries within mpv are never treated as command-line tools. No helper dependencies or packaging manifests changed.

`LocalFirstAudioResolver` waits for restoration, verifies the completed local file, then uses ordinary streaming only when the shared synchronous `PlaybackNetworkPolicy` allows it. Missing/damaged downloads become missing and are unavailable offline; online fallback does not silently redownload them. Local `loadfile` commands use per-file lavf protocol restrictions without changing later streaming commands. `MusicLibrary` persists strict-boolean `offlineMode`; switching cancels Search/playback/recommendations and stops transport. Offline guards also cover recommendation prefetch/advance and Next capability. The existing generation invalidation rejects late online results. New downloads are cancelled/blocked offline; leaving offline requires explicit Play/Retry. Existing Repeat/manual-queue/Favorites order and media command/lifecycle ownership remain unchanged.

SwiftUI adds `DownloadAction` to `SongRow`, `DownloadsView` to the sidebar, confirmation-based managed-file deletion/clear, progress/status/error/retry displays and completed storage totals. The Offline Mode switch is next to Autoplay under the transport. Deleting a currently playing local download through this UI stops it first. The existing library and download persistence banners separately expose errors and Retry.

## Repeat and Favorites sequence

`MusicLibrary` owns a transient ordered Favorites snapshot and cursor, independent of the persistent manual queue. Play All captures the existing alphabetically sorted SQLite-backed Favorites (video ID breaks title ties); Shuffle captures a permutation once. New favorites wait for a new snapshot. Removed favorites are excluded from future automatic selections, including wraparound; removal never interrupts the current song. A one-song snapshot works with every repeat mode. Empty Play All/Shuffle is a no-op and the controls are disabled.

Natural completion first honors Repeat One, then consumes one manual queue entry, then advances the snapshot cursor, then wraps the eligible snapshot for Repeat All, otherwise permits opted-in Phase 2B continuation or stops. Manual Next bypasses Repeat One and uses the same queue/sequence selection. Queue selections do not move the playlist cursor, so a queue inserted during favorite A resumes at B after its last entry. Play All/Shuffle explicitly starts its first favorite while preserving upcoming queue entries for the next transition. A manual queue is never captured for Repeat All. Direct single-song Play ends the playlist context; Repeat All applies only to an active Favorites snapshot. Repeat One also works on direct and queued songs.

Previous retains its existing seek-to-start behavior above three seconds. Earlier navigation entries carry sequence identity/cursor so revisiting a track within the current playlist also restores the correct continuation. Returning to a selection from an older sequence ends the current playlist context. Navigation history is bounded to 100 entries for indefinite Repeat All sessions. Stop retains the session snapshot for explicit Play/Next; relaunch restores only existing current-track metadata and manual queue, never a playlist or autoplay.

Every transition goes through the existing generation invalidation and serialized resolver/player tasks. Duplicate EOF and stale remote commands cannot advance again. A repeat is a fresh resolved attempt and counts History only after audio starts. EOF before a positive clock fails visibly. Resolution/decoder/IPC errors stop with Retry; no automatic retry, skipping, or repeat loop occurs. Next can explicitly bypass an unavailable favorite. Failed unstarted manual selections retain the existing queue-recovery behavior.

`repeatMode` is an Off/One/All raw string in the injected UserDefaults, with missing/invalid values defaulting to Off. Changing modes immediately refreshes media-command availability. SwiftUI uses SF Symbols, an active color/background, help, and VoiceOver value. Existing current-row highlighting also identifies the playing favorite. No SQLite migration, new database, stream persistence, engine/runtime-discovery, media registration, or window-lifecycle change is needed.

## Phase 1.5 — History management

History deletion is centralized in `MusicLibrary`. A row deletion matches its stable History UUID; Clear requires a pending confirmation with explicit Cancel/Clear actions. Mutations optimistically update only History, then use the existing coalescing writer and revision-checked SQLite snapshot transaction. Referenced song metadata is retained through Favorites/Queue/session foreign keys. No audio files are accessed, no schema migration is required, and active playlist/cursor, pending queue selections, playback generation, and the current attempt's History-recorded flag are untouched. Consequently deleting the current row does not recreate it on the next position update; a later new play can create a fresh row/count.

`historyRetention` and `historyLimit` are validated raw strings in the injected UserDefaults. Missing/unknown values choose Never/Unlimited, replacing the old automatic 100-song cap without removing any previously saved entries. Retention choices are Never, 7, 30, or 90 elapsed 24-hour days since last play. Count choices are Unlimited, 100, or 500 distinct songs. Cleanup removes age-expired rows (timestamp at or before cutoff), then trims the oldest remaining rows, preserving newest-first order and stable identities. Preference changes apply immediately. Cleanup also runs after restoration and before/after recording a newly started track, ensuring expired counts do not carry into a new play.

A cancellable, weakly capturing main-actor task schedules the oldest row's expiry, rechecking at least daily for wall-clock changes. It needs no open window or new playback. Successful/attempted quit and shutdown cancel scheduling; a failed persistence flush re-enables it. While closed there is no background service; the next restoration applies the policy. Restoring/closing guards prevent edits to incomplete or closing state. Never/Unlimited performs no age/count deletion. Raising limits does not resurrect removed rows. Defaults do not recover entries already evicted by older builds.

SQLite schema v2, migration/rollback, bound SQL, serialized saves, revision conflicts, and corruption handling remain unchanged. Only the old History-specific 10,000-row save guard is removed to support Unlimited honestly; Favorites/Queue retain their existing caps. The SQL progress deadline and resource limits still apply, reporting a visible unsaved error and preserving the prior transaction on failure. Unlimited is not a claim of unbounded memory or constant-time full-snapshot saves. Tests cover a 10,002-entry persisted/reopened History and deletion failure/retry using isolated settings/databases.

## Phase 2B — recommendations and transition ownership

`RelatedSongProviding` is a Sendable boundary independent of search and audio resolution. `YouTubeMixProvider` is an actor using existing ToolLocator/FoundationProcessRunner, including bundle-relative discovery and cancellation/pipe limits. It builds only validated watch-Mix URLs (`watch?v=ID&list=RDID&start_radio=1`) and fixed metadata-only argument arrays. Each subprocess has a 30-second deadline, 4 MiB stdout limit, 10-second socket timeout and bounded retries; at most one unavailable-Mix search follows, so two processes can take about 60 seconds in total. No cookies, account access, dependency installation, downloads, or signed-stream persistence is introduced.

A playlist object and expected RD ID are required for Mix. Bounded decoding rejects malformed IDs/titles/durations, private/deleted/unavailable/live/upcoming entries, and duplicate IDs. Missing structured artist metadata is normal: display channel/uploader or Unknown channel. Missing duration remains unknown. A valid batch filtered to no unseen songs stops; it does not trigger repeated Mix requests or search. Only explicit unavailable/empty Mix data permits one search using artist/channel plus `official audio`, with `.searchFallback` provenance. Malformed or transport failures never silently masquerade as Mix-unavailable. Rate-limit/auth diagnostics stop immediately without fallback. Fixed errors replace raw diagnostics in the UI.

The provider holds one 20-song, 60-second cache, reapplying caller exclusions on cache hits; one in-flight call prevents parallel extractions. Rate/auth failure imposes a 120-second cooldown; other provider failures impose 30 seconds. Cooldown does not schedule an automatic retry. Retry requires a later explicit selection/toggle after cooldown. Cancellation does not count as a service error.

MusicLibrary owns the session-only buffer, source label, 50 recent selection IDs, 50 requested seed IDs and request epoch. Recent History (up to 50), current selection and upcoming manual queue entries are excluded. Exclusions are rechecked both when a request returns and when consuming candidates. A seed is requested once while retained in the bounded session window. Prefetch starts after actual positive audio position, or explicitly enabling Autoplay on an already started track. It only refills an empty buffer, preserving snapshot order across manual detours. Direct Play/Play All/Previous to another track starts a new recommendation session; seek-to-start retains the session. No automatic candidate enters the persisted queue or Favorites.

Completion and manual Next still enter one main-actor selector: Repeat One applies only at natural EOF; otherwise queue, remaining Favorites, Repeat All wrap, eligible opted-in radio, then stop. Natural successful EOF resets consecutive automatic failure count. Audio candidates go through the existing serialized generation-aware resolver/mpv load path. Only automatic tracks can skip failures, with a maximum of three consecutive failures; manual/Favorites errors retain Retry. A fresh stream is resolved for every load. After successful automatic playback, normal History accounting applies.

If a recommendation is still in flight when continuation is needed, the library invalidates the prior playback generation, cancels any prior resolution, serializes an engine Stop, and enters a cancellable waiting state. This also stops audible audio when manual Next arrives before recommendations. On completion it rechecks queue/playlist/mode and only the current session may advance. A new manual queue entry while waiting advances immediately. Manual Next carries genuine pause through buffering and delayed recommendation selection. Pause/Toggle while waiting cancels continuation; Stop, shutdown, sleep/output interruption and quit invalidate/cancel requests and disarm continuation. Late provider data and stale EOF/media commands cannot restart playback. Loading/waiting commands and metadata use the existing system-media publication path.

`autoplayEnabled` is a strict stored boolean, default Off. Preference restoration alone does not arm a session, launch a helper, or start recommendations/audio. SQLite schema/snapshot and persistent session recovery remain unchanged. Only selected/started automatic songs enter existing current-track/History persistence; recommendation buffer, provenance, tasks, epochs, cooldown and stream references are transient. No automatic play occurs after relaunch or wake. The player switch, provenance label and subdued loading/failure text live beneath the transport row, without changes to other library screens.

The Phase 2A empirical report remains local under ignored `.build/phase2a-research/REPORT.md`. Watch-Mix extraction and limited playback were demonstrated, while bare RD playlist URLs failed and Music URLs redirected. Missing artist data, unstable suggestions, service throttling, JavaScript runtime requirements for some formats, and unavailable videos remain limits; no service-wide reliability claim is made.

## Native playback

SwiftUI observes the main-actor `MusicLibrary`. Search remains explicit/cancellable through `SongSearching` and bounded Swift `Process` execution. Playback uses `AudioStreamResolving` → `MPVPlaybackEngine` → `MPVConnection`. The audio-only selector remains `bestaudio[protocol^=m3u8]/bestaudio`, addressing the reproduced direct-stream HTTP 403 without headers, cookies, client overrides, or added dependencies. [YOUTUBE_PLAYBACK_DIAGNOSIS.md](YOUTUBE_PLAYBACK_DIAGNOSIS.md) records the Checkpoint 3 investigation.

One owned, idle audio-only mpv child is started only for playback. Its private 0700 `mkdtemp` directory contains the Unix IPC socket. Newline-framed JSON uses request IDs, observed properties, generation UUIDs, and playlist entry IDs; stale requests and duplicate EOF cannot consume extra queue entries. Startup/command/load deadlines and process termination/cleanup remain. Raw signed URLs/diagnostics are not logged; mpv disk caching and saved playback positions are disabled.

## Persistence boundary

`LibraryPersisting` exposes async load, atomic snapshot save with expected revision, and close. Sendable snapshots contain only songs, favorite dates, aggregated History, ordered queue identities, current-track metadata, a recoverable queued selection, and revision. Production explicitly injects `SQLiteLibraryStore` in the App. A model without a store is intentionally ephemeral for unit tests; tests that exercise persistence inject temporary database URLs. No test opens the user's real database or uses their UserDefaults domain.

`SQLiteLibraryStore` is an actor. Its connection/statements are created, used, finalized, and closed on that actor, away from SwiftUI. The macOS SQLite3 library is linked directly, with no ORM/third-party package. All values use prepared statements/bound parameters. SQL identifiers and control statements are static.

The Debug location is `~/Library/Application Support/MangoMusic/library.sqlite3`, resolved through the per-user Application Support API. A sandboxed build resolves its container's corresponding location. New directories/files use 0700/0600. Foreign keys are enabled, WAL and synchronous FULL are used, lock waits are bounded at 250 ms, and a progress handler interrupts long SQL operations after roughly three seconds. These bounds do not guarantee deadlines for a stalled filesystem/OS call.

## Schema and migrations

`PRAGMA user_version` is 3. Timestamps are real Unix seconds; optional durations are seconds/NULL. The in-memory identifier is `youtube:<11-character ID>`; the database stores the validated raw eleven-character ID.

| Table | Key and contents |
| --- | --- |
| `songs` | `video_id` primary key with ID check; nonempty title, artist/channel, optional bounded finite duration |
| `favorites` | `video_id` primary key/foreign key; `added_at` |
| `history` | `video_id` primary key/foreign key; unique row UUID `entry_id`, `played_at`, positive `play_count` |
| `queue` | UUID `entry_id` primary key; song foreign key; unique contiguous nonnegative `position` |
| `downloads` | Raw stable video ID primary key; canonical source, copied title/artist/duration, attempt UUID, status, unique managed path, actual format, bytes, timestamp, SHA-256, safe error |
| `download_state` | Singleton independent nonnegative downloads revision |
| `session` | Singleton `id=1`; optional current song; optional pending queue UUID/song pair; nonnegative `revision` |

`history_recent(played_at DESC, video_id)` supports recent-first ordering with deterministic timestamp ties. The primary/unique indexes support song references, favorite deduplication, queue identity, and position. Foreign-key/integrity checks and decoded-value validation reject broken data rather than silently dropping rows.

A fresh empty version-0 database creates the internal version-1 schema and migrates to version 3 in one transaction. Version 2 → 3 adds independent downloads and download_state tables without replacing any collection/session rows. Older schema-v2 applications refuse v3 safely; this is forward migration, not downgrade support. Version 1 → 2 adds `play_count` with default 1 for existing History rows and the recent-history index, preserving data. Version 1 is an internal migration baseline, not a database shipped in Checkpoint 3. Schema verification runs before commit. Failed migrations roll back; future versions and unrecognized nonempty version-0 files are refused. No corruption recovery path deletes, renames, resets, or replaces the user's database automatically. Preserve a closed-app backup of the complete folder, including any sidecars.

## Serialized saves and errors

Library mutations are centralized; the view no longer directly edits the queue array. The UI updates optimistically and exposes Saving/unsaved state. One main-actor writer task captures a snapshot, awaits the store, then writes the newest snapshot if edits arrived meanwhile. Edits during an in-flight save are not lost; rapid actions coalesce. A write transaction checks the database revision, upserts referenced song metadata, replaces collection/session rows, and removes only unreferenced song metadata. All steps commit together or roll back. Known duration is retained when incoming metadata lacks it. Successful commit advances the revision; a stale instance fails instead of overwriting another instance's changes.

On failure, the last committed database and in-memory edits remain, a fixed error is visible, and Retry explicitly retries saving. The unsaved indicator only clears when the newest snapshot commits. This makes an optimistic favorite heart distinct from confirmed durable saving. Load failure disables library actions until Retry succeeds; settings remain independent. Conflict merging is intentionally unsupported. A stale-instance conflict may require external reconciliation/preserving in-memory edits before reopening; Retry does not override the revision safeguard.

## History and queue semantics

A play is counted on the first positive mpv position after file-loaded while playing. File-loaded alone, selection/queuing, or a failed start does not count. History has one row per song, stable row UUID, most recent timestamp, and accumulated count, with configurable age/count retention (Never/Unlimited by default). Pause/resume, seek, and Retry in the same selected attempt do not increment again. An explicit Play after Stop/completion or a new selection starts a new counting attempt. Removing an old row under retention also removes its prior count. Individual removal and confirmed Clear History are available in Phase 1.5.

Upcoming entries have stable UUIDs, allowing intentional duplicate songs. Play Next prepends, Add appends, and reorder/remove/clear persist. Direct search playback leaves the upcoming queue intact. Selecting a queued entry removes it from upcoming and retains its UUID/song in `session` until real playback starts. A failed/interrupted unstarted selection is put back at the front when switching away/Stop/quit/restoration, with UUID deduplication; if it was already present its order is preserved. While stopped that reference allows Play to consume the same recovered entry once. Removing/clearing that recovered upcoming item clears its recovery reference. Clear Queue otherwise affects upcoming items, not an active selection.

The first qualifying position clears the recovery reference and records History atomically with the resulting queue snapshot. If a crash precedes that commit, the last committed recovery reference can replay an interrupted item rather than lose it (at-least-once recovery). Successfully started current items stay consumed after relaunch. EOF follows the repeat/manual-queue/Favorites/opt-in-radio policy above; manual/Favorites failure stops with Retry and automatic failures are bounded. Duplicate/stale completion events are ignored. Optional recommendations follow only after the explicit queue/finite-playlist rules in Phase 2B; there is no unrelated automatic startup.

## Startup, settings, and quit

Startup restores collections and current-track metadata asynchronously, while actions are disabled. Current position is zero, playback is stopped, and no stream is resolved or mpv launched. Pressing Play is an explicit new playback attempt with a freshly resolved URL. Playback navigation-back history, transient pause/buffering/errors, and signed URLs are not saved. UserDefaults restores finite numeric volume clamped to 0–1 (invalid/missing → 0.7) boolean sidebar state (invalid/missing → expanded), and validated repeat mode (invalid/missing → Off). Light/Dark remains system-adaptive.

`applicationShouldTerminate` uses `.terminateLater`. The library blocks new edits, cancels search, stops playback/returns any unstarted queued selection, flushes the latest save, then terminates owned mpv, closes SQLite, and replies to AppKit. Failed flush cancels quitting, retains edits, keeps the store/player usable, and shows the recoverable error. No async write is entrusted solely to `willTerminate`; its playback cleanup remains idempotent. Normal window closure keeps the library/player alive, and the existing openWindow action handles Dock reopening.

## Checkpoint 5 — one controller and native adapters

`MusicLibrary` is the authoritative main-actor controller. Its transient requested-pause intent is distinct from actual mpv-observed pause/position. Rapid toggles alternate the latest intent instead of repeatedly using a delayed acknowledgement. Explicit Play/Pause are idempotent. UI and remote command availability derive from the same capability set; seeking requires a loaded, non-ended track and known duration. Previous/Next while genuinely paused pass an initial pause into the engine before loadfile, avoiding a brief audible start. Errors are distinct from a genuine user pause, so an explicit Next after error starts the chosen queued item. Pause during resolution cancels/returns the pending item and rejects late results. None of these transient fields enters SQLite.

`SystemMediaIntegration` is owned by the application delegate, never a window/view. Repeated onAppear/attach is idempotent. It subscribes to model changes through an observation-ignored main-actor callback; closing a window does not tear it down. The public macOS adapters are `NativeSystemMediaAdapter` (MediaPlayer) and `NativePlaybackLifecycle` (NSWorkspace/CoreAudio). Protocols and pure snapshot/publication policy allow offline/hardware-free tests. The existing local Space/Return and menu shortcuts remain; there is no new global keyboard monitor or permission requirement.

MediaPlayer callbacks arrive on an unspecified executor. `MediaCommandGate` protects only enabled kinds, generation and registration epoch with a lock, copies a Sendable command payload, and schedules work on the main actor. It never sends an MPRemoteCommandEvent across actors or synchronously blocks the main queue. The model rechecks capabilities and playback generation before executing. A Next accepted for a prior track is discarded after EOF/UI advancement, preventing a second consumption. Handler return success means accepted for dispatch, not that future asynchronous IPC is guaranteed to succeed. Registration epochs reject callbacks queued before teardown/re-registration.

Seven owned target tokens implement Play/Pause/Toggle/Next/Previous/absolute Seek/Stop. Unsupported continuous seek/skip/rate/repeat/shuffle/rating/language commands are disabled. Only owned tokens are removed; no removeTarget(nil) broad removal. Capability setters are cached to avoid repeated native setter work on every position event. Actual OS command routing is subject to Now Playing app arbitration and hardware/firmware support.

## Now Playing publication and platform scope

The normalized snapshot publishes title, optional artist/duration, elapsed seconds, rate/default rate, and audio media type. It omits empty artist/unknown duration, clamps invalid time, and contains no stream URLs, artwork, IPC paths, tokens, or persistence data. Playing anchors use rate 1; paused/loading/buffering anchors use rate 0. Buffering retains the playing command/state intent while freezing extrapolated time. Loading is represented as paused/rate-zero until actual load. Stop/error/exhaustion/quit clears nowPlayingInfo and sets macOS playbackState stopped. A restored current track is not published as active media on startup.

Apple extrapolates elapsed time. Ordinary clock updates are anchored at most once per five seconds, with immediate updates on generation/title/artist/duration/phase changes, significant clock discontinuities, and mpv playback-restart seek anchors. No polling timer or synthetic player clock was added. mpv remains the source of actual position/state; command intent affects button/capability responsiveness, not fabricated elapsed time.

The installed SDK declares these MediaPlayer APIs available from macOS 10.12.2, so they fit the macOS 14 target. macOS requires explicit MPNowPlayingInfoCenter.playbackState; no iOS AVAudioSession or unavailable multi-player session API is used. No Music-library authorization, microphone capture, Accessibility permission, private MediaRemote API, or device-specific Bluetooth stack was introduced. Runtime readback on macOS 26.7.1 verifies API acceptance and handler/listener cleanup; it does not itself prove visible system UI or hardware delivery. A subsequent user test of commit `4d1701ceffeb693b1117f0b0df41c90c3b565806` independently confirms Xcode launch, audible playback, Control Center rendering and Play/Pause/Next/Previous, playback and Control Center commands while the window is closed, Dock reopening, and Cmd+Q stopping playback/quitting without visible errors on this Mac. Physical keyboard media keys, Bluetooth headphone controls, system-level seeking, physical sleep/wake, output-device changes, and process-level orphan checks remain manually unverified. Lock-screen UI and other device/surface compatibility are not established; Cmd+Q stopping sound does not constitute a process-level cleanup inspection. Some system surfaces do not expose scrubbing; absolute seek is advertised only when capable. No API newer than the macOS 14 deployment target is required.

The child mpv is started with media-controls and input-media-keys disabled to prevent a second Now Playing owner/command path. stop-screensaver is disabled as well; mpv 0.41.0 is the validated dependency. No entitlement or Debug/Release policy change was made.

## Interruptions and teardown

NSWorkspace willSleep/didWake and a CoreAudio default-output listener live at app scope. Listener/observer registration is idempotent, uses registration epochs, and is removed on teardown (native removal status is verified). Device-ID equality filters duplicate route notifications. System sleep invalidates the generation and releases an owned child even when idle, so a queued pre-sleep Play cannot become actionable again after wake. An actual default-device change stops active playback/resolution. Both interruption paths preserve pending manual entries through the existing serialized SQLite writer and terminate the owned child synchronously. The IPC cleanup task is awaited before an explicit later load. Wake only restores command capability; it never launches/resolves/resumes. Explicit Play restarts the current track with a fresh stream from the beginning. This conservative policy avoids unexpected output after headphones disconnect. Display sleep/focus changes do not stop playback, and no keep-awake assertions exist.

Ordinary pause/seek/volume/navigation reuses one persistent process. After an interruption a later explicit playback may start a replacement, after the previous child/socket cleanup; tests check actual PID exit and paused seek/reload. Network/decoder/startup failures keep the existing explicit error/Retry path and never silently skip. No automatic reconnection loop was added.

Cmd+Q still uses the SQLite flush/terminateLater handshake. Commands are disabled and metadata clears when closing; a failed flush cancels quit and re-enables applicable commands while preserving unsaved edits. On actual termination the delegate tears down media targets/output/workspace observers, clears metadata, and performs idempotent owned-player cleanup. No schema migration or changed persistence format was needed for Checkpoint 5. Prior schema/queue/privacy documentation above remains applicable.

The implementation follows Apple's [MPNowPlayingInfoCenter](https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfocenter), [macOS playbackState](https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfocenter/playbackstate), and [MPRemoteCommandCenter](https://developer.apple.com/documentation/mediaplayer/mpremotecommandcenter) APIs and the [mpv option reference](https://mpv.io/manual/stable/). Manual proof and test counts are recorded in [VALIDATION.md](VALIDATION.md); archived Checkpoint 4 evidence remains in [VALIDATION_CHECKPOINT4.md](VALIDATION_CHECKPOINT4.md).


## Checkpoint 6 — local Release packaging

The packaging boundary is independent of playback state and persistence. Scripts/Packaging explicitly acquires checksum-pinned upstream archives and build-only wheels into ignored .build/packaging, then builds static minimal mpv/FFmpeg and their required dependencies with arm64/macOS 14 flags. mpv links only system libraries/frameworks; no video GPU backend, Lua scripting, or mpv yt-dlp integration is enabled. CoreAudio output and system SecureTransport HTTPS, HLS/fMP4/MPEG-TS and audio decoding/resampling remain. The upstream CoreAudio initialization backport from the development Homebrew formula is retained. libass/libplacebo are upstream mandatory dependencies even for this audio use.

The app's existing Process launch and persistent JSON socket architecture are retained. The package includes a MangoBundledTools Info.plist marker. ToolLocator uses Bundle.main-relative Contents/MacOS paths, checks native executable headers/permissions and rejects symlink helpers; a missing/damaged packaged helper cannot be masked by global installations. Full signature/embedded library integrity is checked by the packaging validator; header inspection is not a complete runtime integrity check. Existing explicit dependency injection remains for tests; the production app does not accept executable override paths from environment variables. Search and stream resolution share lookup. Packaged helper PATH excludes Homebrew and installed Python. Development builds retain external lookup and their scripting opt-out flags; scripting options are omitted only for the compiled-without-scripting packaged mpv.

Standalone upstream yt-dlp contains its own Python, native extensions, TLS/certificate and Python package runtime. All 103 embedded native files are audited for arm64, deployment minimum and bundle/system library resolution. No Deno is bundled; the tested public search/HLS path works without a JavaScript runtime. Upstream format/extractor changes or other videos can still fail and require a reviewed dependency update.

Packaging overrides ENABLE_APP_SANDBOX=NO only for its Release command. This preserves subprocess, Unix IPC and the existing per-user Application Support path while granting ordinary user filesystem/network permissions rather than sandbox confinement. It adds no elevated privilege or entitlement and changes no system protection. Main app and helpers are ad-hoc signed, with the outer bundle signed last; no distribution or App Store compatibility follows. Existing Xcode Debug and stock Release settings remain unchanged. Metadata, icon, bundle identifier, SQLite schema and UserDefaults behavior are retained. See PACKAGING.md and VALIDATION.md for current evidence and manual limits.
